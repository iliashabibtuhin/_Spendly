## Overview and architecture

Two independent npm projects. There is no root `package.json`.

| Folder | Stack |
|---|---|
| `client/` | React 19, Vite 8, Tailwind CSS v4, React Router 8, Recharts 3, Zod 4 |
| `server/` | Node.js, Express 5, Prisma 7 with PostgreSQL (`@prisma/adapter-pg`), JWT + bcryptjs, Zod 4 |

Production layout:

```
Browser ──> Vercel        static build of client/ (single-page app)
   │
   └── HTTPS + "Authorization: Bearer <token>" ──> Render   Express API (server/), all routes under /api
                                                      │
                                                      └──> Neon   PostgreSQL
```

- The web app and the API are on **different origins** in production (`*.vercel.app` and `*.onrender.com`), so the API must allow the web app's origin through CORS (`CLIENT_ORIGIN`).
- In local development the web app calls `/api` on its own origin and Vite proxies it to Express, so CORS never comes into play.
- Login uses a JWT stored in the browser's `localStorage` and sent as a Bearer header. No cookies are used.

```
server/
  prisma/
    schema.prisma        data model (User, Category, Transaction, Budget)
    migrations/          PostgreSQL migration history (commit these)
    seed.js              optional demo account
    import-sqlite.js     optional one-off import of the old SQLite dev.db
    archive/             old SQLite migration, kept for reference only (not applied)
  prisma.config.ts       Prisma 7 CLI config (schema path, DATABASE_URL, seed command)
  src/
    index.js             entry point (starts HTTP server, graceful shutdown)
    app.js               Express app: helmet, CORS, JSON, /api router, error handler
    config/env.js        validates environment variables; the server refuses to start if invalid
    lib/prisma.js        Prisma client with the PostgreSQL (pg) driver adapter
    middleware/          auth (JWT), validate (Zod), errorHandler
    validators/          Zod schemas for every body, query and route param
    services/            business logic and all database access
    controllers/         thin HTTP handlers
    routes/              route table
    generated/           Prisma client, generated by `npm install` (git-ignored)
client/
  vercel.json            SPA rewrite so deep links (e.g. /transactions) work on Vercel
  vite.config.js         dev proxy for /api
  src/
    main.jsx             entry point
    lib/api.js           API client (reads VITE_API_URL)
    context/, hooks/, components/, pages/
```

## Local development

Everything in this section is for your own machine. Production commands are in [Production deployment](#production-deployment).

### 1. Start a local PostgreSQL database (pick one)

```bash
# A) Docker
docker run -d --name spendly-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=spendly -p 5432:5432 postgres:17
#    DATABASE_URL="postgresql://postgres:postgres@localhost:5432/spendly"

# B) Native PostgreSQL install
createdb -U postgres spendly
#    DATABASE_URL="postgresql://postgres:<your password>@localhost:5432/spendly"

# C) No install: Prisma's local Postgres (run inside server/ after `npm install`, keep it running)
npx prisma dev
#    use the "TCP" postgres://... URL it prints

# D) A Neon "dev" branch: use its connection string (see Neon below)
```

### 2. API (`server/`)

```bash
cd server
cp .env.example .env        # Windows PowerShell: Copy-Item .env.example .env
# edit .env: set DATABASE_URL (step 1) and JWT_SECRET (see "Environment variables")
npm install                 # also runs `prisma generate`
npx prisma migrate dev      # applies the migrations to your local database
npm run db:seed             # optional: demo account demo@spendly.app / demo1234 with 6 months of data
npm run dev                 # http://localhost:4000  (check: http://localhost:4000/api/health)
```

### 3. Web app (`client/`, second terminal)

```bash
cd client
cp .env.example .env        # defaults are correct for local development
npm install
npm run dev                 # http://localhost:5173
```

Open http://localhost:5173 and register, or sign in with the demo account if you seeded it.

### Changing the database schema (development only)

```bash
cd server
# edit prisma/schema.prisma, then:
npx prisma migrate dev --name describe_the_change   # creates + applies a new migration
npx prisma generate                                 # Prisma 7 does NOT generate automatically on migrate
```

Commit the new folder under `prisma/migrations/`. Render applies it on the next deploy. **Never run `migrate dev` or `migrate reset` against the production (Neon) database.**

## Environment variables

Only the `.env.example` templates are committed. Real `.env` files are git-ignored and must never be committed or shared.

### Backend: `server/.env` locally, Render "Environment" in production

| Variable | Required | Secret | What it does | Where to get the value |
|---|---|---|---|---|
| `DATABASE_URL` | **Yes** | **Yes** | PostgreSQL connection string, used by the app and by the Prisma CLI (migrate, seed) | Local: from your database (see above). Production: Neon → your project → **Connect** → copy the **direct** (non-pooled) string. Format: `postgresql://USER:PASSWORD@ep-xxxx.REGION.aws.neon.tech/neondb?sslmode=require` |
| `JWT_SECRET` | **Yes** | **Yes** | Signs login tokens. At least 32 characters, and not the placeholder from `.env.example`. | Generate: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`. Use a **different** value for production than for local. Changing it signs everyone out. |
| `CLIENT_ORIGIN` | Yes in production | No | Origin(s) allowed by CORS, comma-separated, exact match. Default: `http://localhost:5173` | Your Vercel URL, e.g. `https://spendly.vercel.app`. See [CORS](#cors). |
| `JWT_EXPIRES_IN` | No | No | Token lifetime, e.g. `7d`, `12h`. Default: `7d` | Your choice |
| `NODE_ENV` | No | No | `development` (default), `production` or `test` | Set `production` on Render |
| `PORT` | No | No | HTTP port. Default: `4000` | **Don't set it on Render**; Render provides it |
| `NODE_VERSION` | No (Render only) | No | Node version Render uses for the build and runtime | Set `24` |

The server checks these variables at startup and exits with a clear message if one is wrong (see [Troubleshooting](#troubleshooting)).

### Frontend: `client/.env` locally, Vercel "Environment Variables" in production

| Variable | Required | Secret | What it does | Value |
|---|---|---|---|---|
| `VITE_API_URL` | Yes on Vercel | **No, it is public** | Base URL of the API. **Built into the JavaScript at build time.** | Local: `/api`. Production: Render URL + `/api`, no trailing slash, e.g. `https://spendly-api.onrender.com/api` |
| `API_PROXY_TARGET` | No (local only) | No | Where the Vite dev server forwards `/api` | `http://localhost:4000`. Not used on Vercel. |

Every `VITE_*` value ends up in public JavaScript. **Never put a secret in a client variable.**

## Production deployment

Order matters: **GitHub, then Neon, then Render, then Vercel, then back to Render** to set `CLIENT_ORIGIN`.

### 1. GitHub repository

The project was handed over without git history. Create the repository from the project root:

```bash
cd Spendly
git init
git add .
git status            # check: NO .env, dev.db, node_modules, dist or src/generated in the list
git commit -m "Initial import of Spendly"
# create an empty repo on github.com (no README/.gitignore), then:
git branch -M main
git remote add origin https://github.com/<you>/spendly.git
git push -u origin main
```

`.gitignore` already excludes `.env` and `.env.*` files (except `.env.example`), `*.db`/SQLite files, `node_modules/`, `dist/`, `server/src/generated/` and platform folders (`.vercel/`).

### 2. Neon (database)

1. Sign in at neon.tech, then **New Project**. Pick a region close to your Render region; for Bangladesh, Singapore (`aws-ap-southeast-1`) is a good choice. Use PostgreSQL 16 or 17.
2. Open the project and click **Connect**. Select the database (default `neondb`) and **turn "Connection pooling" off**. Copy the connection string. This is the production `DATABASE_URL`.
   - Use the **direct** string because `prisma migrate deploy` runs with the same variable, and Prisma migrations should not run through the pooler.
3. Keep this string secret. You will paste it into Render.
4. Optional: create a separate Neon **branch** (e.g. `dev`) for local development, so you never develop against production data.

You don't need to create tables by hand. Render's build runs the migrations.

### 3. Render (API)

Render dashboard → **New → Web Service** → connect your GitHub repo.

| Setting | Value |
|---|---|
| Root Directory | `server` |
| Runtime | Node |
| Build Command | `npm ci --include=dev && npm run db:deploy` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |
| Region | Same as (or close to) your Neon region, e.g. Singapore |

Environment variables (**Environment** tab):

| Key | Value |
|---|---|
| `DATABASE_URL` | Neon direct connection string |
| `JWT_SECRET` | New random value (generate as described above) |
| `CLIENT_ORIGIN` | Temporarily `http://localhost:5173`; replace with the Vercel URL in step 5 |
| `NODE_ENV` | `production` |
| `NODE_VERSION` | `24` |
| `JWT_EXPIRES_IN` | Optional, e.g. `7d` |

Do **not** set `PORT`.

Why the build command looks like that:
- `--include=dev` is needed because the Prisma CLI is a devDependency. With `NODE_ENV=production`, plain `npm ci` would skip it and the `postinstall` step (`prisma generate`) would fail.
- `npm run db:deploy` runs `prisma migrate deploy`. It applies only the committed migrations, never creates new ones, and is safe to run on every deploy.

After the deploy, open `https://<your-service>.onrender.com/api/health`. It should return `{"ok":true}`.

Notes:
- Free Render instances sleep when idle. The first request afterwards can take 30–60 seconds, and the web app may briefly show "Can't reach the Spendly server".
- **Optional demo account:** `npm run db:seed` creates `demo@spendly.app` with the **publicly known** password `demo1234`, so only run it if you want a public demo. Render's Shell isn't available on free instances, so run it from your machine against Neon, inside `server/`. A variable set in the shell takes precedence over `server/.env`.
  ```bash
  DATABASE_URL="<neon direct url>" npm run db:seed                        # bash / macOS / Linux / Git Bash
  $env:DATABASE_URL="<neon direct url>"; npm run db:seed                  # Windows PowerShell
  ```

### 4. Vercel (web app)

Vercel dashboard → **Add New → Project** → import the same GitHub repo.

| Setting | Value |
|---|---|
| Root Directory | `client` |
| Framework Preset | Vite |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Install Command | default (`npm install`) |

Environment variable:

| Key | Value | Environments |
|---|---|---|
| `VITE_API_URL` | `https://<your-service>.onrender.com/api` | Production (and Preview if you use previews) |

`VITE_API_URL` is read **at build time**. After changing it, **redeploy** the project, because just saving the variable has no effect. `client/vercel.json` rewrites every path to `index.html`, so reloading `/transactions` or `/budget` works.

### 5. Connect the two: set `CLIENT_ORIGIN`

1. Copy your Vercel production URL, e.g. `https://spendly.vercel.app`.
2. In Render → Environment, set `CLIENT_ORIGIN=https://spendly.vercel.app` and save. Render redeploys.
3. Open the Vercel URL. Register, add a transaction, check the dashboard and budget, and reload a deep link such as `/transactions`.

### Deploying updates later

- Push to `main`. Render and Vercel redeploy automatically.
- Schema changes: create the migration locally with `npx prisma migrate dev --name ...` and commit it. Render's build applies it with `migrate deploy`.

## CORS

The API (`server/src/app.js`) allows only the origins listed in `CLIENT_ORIGIN`.

- **Exact match:** the scheme, host and port must match what the browser shows, for example `https://spendly.vercel.app`. A trailing slash is stripped automatically. Wildcards are **not** supported.
- **Several origins:** separate them with commas, e.g. `https://spendly.vercel.app,https://www.yourdomain.com`.
- **Vercel preview deployments** have their own URLs (e.g. `spendly-git-feature-you.vercel.app`) and are blocked unless you add them. Production-only use needs only the production URL.
- **Custom domain:** add it to `CLIENT_ORIGIN` after attaching it in Vercel.
- **Local development** needs no CORS configuration, because Vite proxies `/api`.
- Requests use a Bearer header, not cookies, so no credentials or cookie settings are required.

In the browser, a CORS failure looks like a network error. The app shows "Can't reach the Spendly server", and the DevTools console shows "blocked by CORS policy".

## Optional: importing the old SQLite data

Spendly originally used SQLite (`server/dev.db`). If the previous developer's local data needs to move to PostgreSQL, use the one-off import script. Most deployments **don't need this**: a fresh database plus registering accounts (or seeding the demo) is enough.

**Requirements and warnings:**
- **It requires the original `dev.db` file.** That file is not in the repository: it is git-ignored on purpose, because it contains user accounts, password hashes and financial data. It must be handed over privately, and only if needed.
- **The target PostgreSQL database must be empty and freshly migrated.** The script refuses to run if any user being imported already exists. In particular, **don't run `db:seed` first**: the old `dev.db` already contains `demo@spendly.app`, so a seeded database will block the import.
- Requires Node.js 22.13+ (it uses Node's built-in `node:sqlite`). A harmless `ExperimentalWarning` may be printed.
- `dev.db` is opened **read-only** and never modified. All rows are inserted in **one transaction**, so a failure leaves PostgreSQL unchanged.
- IDs, timestamps and password hashes are preserved, so the old accounts can log in with their old passwords.

```bash
cd server
# 1. empty database with tables (production: Render's first deploy already did this)
DATABASE_URL="<target url>" npx prisma migrate deploy
# 2. import (reads server/dev.db by default, or pass a path)
DATABASE_URL="<target url>" npm run db:import-sqlite
DATABASE_URL="<target url>" npm run db:import-sqlite -- /path/to/dev.db
```
On Windows PowerShell, set the variable first: `$env:DATABASE_URL="<target url>"`, then run the npm commands.

Expected output: `Found N users, ... Imported. PostgreSQL now has N users, ...`.

The old SQLite migration in `server/prisma/archive/sqlite-migrations/` is kept for reference only. Prisma does not read it.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Server exits with `DATABASE_URL: DATABASE_URL must be a PostgreSQL URL` | `DATABASE_URL` is missing or still an old `file:./dev.db` value. Set a `postgresql://` URL. |
| `JWT_SECRET must be at least 32 characters` or `JWT_SECRET is still the placeholder from .env.example` | Generate a real secret (see Environment variables). |
| Render build: `The datasource.url property is required in your Prisma config file when using prisma migrate deploy` | `DATABASE_URL` isn't set in Render's Environment tab. |
| Render build: `prisma: not found` or the `postinstall` step fails | The build command must be `npm ci --include=dev && npm run db:deploy`. |
| `P1001: Can't reach database server` | Wrong host, or a pooled string where you need the direct one. Check that the URL contains `?sslmode=require` for Neon, and that the local database is running. Neon's free tier suspends idle databases; the first connection wakes them, so retry once. |
| `P1000: Authentication failed` | Wrong user or password in the URL. Copy it again from Neon. Special characters in passwords must be URL-encoded. |
| `P3005: The database schema is not empty` | `migrate deploy` hit a database that has tables not created by these migrations. Use a fresh Neon database or branch. |
| `P3009: migrate found failed migrations` | A previous migration failed part-way. Fix the cause, then `npx prisma migrate resolve --rolled-back <migration_name>` and deploy again. |
| `npm ci` fails: lock file out of sync | Run `npm install` locally in that folder and commit the updated `package-lock.json`. |
| Web app shows "Can't reach the Spendly server" | One of: (1) the Render service is asleep, so wait and retry; (2) `VITE_API_URL` is wrong or the project wasn't redeployed after setting it; (3) CORS, so check the DevTools console and `CLIENT_ORIGIN`. |
| Requests go to `https://<vercel-app>/api/...` and return 404 | `VITE_API_URL` wasn't set when Vercel built. Set it and redeploy. |
| Browser console: `blocked by CORS policy` | `CLIENT_ORIGIN` on Render doesn't exactly match the URL in the address bar (http vs https, www, preview URL). Update it and let Render redeploy. |
| Reloading `/transactions` on Vercel gives 404 | Vercel's Root Directory must be `client` so `client/vercel.json` is picked up. |
| `Too many attempts. Try again in a few minutes.` | Login/register rate limit: 30 attempts per 15 minutes per IP. Wait. |
| Everyone was logged out | `JWT_SECRET` changed, which is expected. Users sign in again. |
| Search, dashboard or another feature behaves differently from local | Compare `migrate status` locally and on Neon: `DATABASE_URL="<url>" npx prisma migrate status`. |
| Import script: `Aborted: these users already exist in PostgreSQL` | The target isn't empty. Use a fresh database (don't seed first). |
| Import script: `No such built-in module: node:sqlite` | Node is older than 22.13. Upgrade Node. |

### Data and security notes

- Money is stored as **integer poisha** (1/100 taka) to avoid floating-point errors. The API takes and returns taka with at most 2 decimals.
- Every query is scoped by the signed-in user's id. Requests for another user's transaction or category return 404, and a transaction can only use a category that the same user owns and whose type matches.
- All totals (dashboard, budget progress, category breakdown, trend) are computed on the server from transaction rows. The client never sends totals.
- Passwords are hashed with bcrypt (12 rounds). Login responses don't reveal whether an email is registered, and auth endpoints are rate-limited per client IP (Express trusts one proxy hop, which is correct for Render).
- Errors use one shape: `{ "error": { "code", "message", "details": { "fields": {...} } } }`.
- Transaction dates are calendar days, stored as UTC midnight.

### API

All routes are under `/api`. Every route except the auth routes and `/health` needs `Authorization: Bearer <token>`.

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | `{ "ok": true }` (Render health check) |
| POST | `/auth/register`, `/auth/login` | returns `{ user, token }` |
| GET | `/auth/me` | current user |
| GET | `/summary?month=YYYY-MM` | totals, balance, budget status, category breakdown, 6-month trend, recent transactions |
| GET | `/transactions` | `search, type, categoryId, from, to, sort=date\|amount, order, page, pageSize` |
| GET / POST / PATCH / DELETE | `/transactions[/:id]` | read / create / update / delete |
| GET / POST | `/categories` | list (optional `?type=`) / create custom |
| PATCH / DELETE | `/categories/:id` | custom categories only; delete is blocked while transactions use the category |
| GET | `/budgets` | recent budgets with spending |
| GET / PUT / DELETE | `/budgets/:month` | budget status / set / remove |
